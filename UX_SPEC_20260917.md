# Autumn SPA 2026 — agreed UX / product specification

Status: AGREED INTERMEDIATE SPEC
Date: 2026-09-17
Trip: 24–31 October 2026, 7 nights

This file is the durable source of truth for the UX/product decisions agreed with the user. Chat history is not the source of truth. Significant later decisions must update this file (or a successor spec) in the repository.

## 1. Page header
- Title: `Осінній SPA · 24–31 жовтня`.
- Show date AND time of the latest meaningful data/content update.
- Scheduler heartbeat alone must not advance the public update timestamp.
- Human-facing latest-update item links directly to the affected hotel card; `Усі оновлення` expands history.
- A dynamic `Знайдено N готелів` count must be visible near the result/filter area and recalculate after scenario/filter changes.

## 2. Global trip scenario
- Switch: `Удвох` | `З дитиною · 10 років`.
- Default: `Удвох`.
- This is not an ordinary filter. It changes price, eligible room/tariff, child placement/food/SPA conditions, integral score, value score, ordering and card content.
- UNKNOWN 2+1 conditions do not silently exclude a hotel; confirmed incompatibility may exclude it.
- In `Удвох`, child-specific information is not rendered at all: no child supplements, beds, kids club, child SPA rules, etc.

## 3. Quick selectors and sorting
Same compact control area; no redundant heading above obvious quick selectors.

Quick selectors:
- `Найкращий SPA`
- `Рідкісні знахідки`
- `Гірський відпочинок`
- `Для дітей` ONLY when the active scenario is `З дитиною · 10 років`; hide it in `Удвох` because it is irrelevant there.

Selectors are independent tags and may overlap. Multiple selected selectors combine as constraints (AND).

Sorting:
- `Рейтинг ↓` — default
- `Ціна / якість ↓`
- `Вартість ↑`

`Рейтинг` is our integral trip-specific score, not Booking rating. `Ціна / якість` is a separate internal value score.

## 4. Region filter
Use administrative oblasts only, not ambiguous mixed tourist/geographic labels.
Examples: Закарпатська, Івано-Франківська, Львівська, Чернівецька, Хмельницька, Тернопільська, Волинська, Житомирська, Черкаська, etc.
- Render only oblasts represented by actual current hotels.
- All active by default.
- Click excludes/includes; visible `✓` / `✕`, not color alone.
- `Гірський відпочинок` is a separate trip-character tag, not a region. It means mountains are a defining part of the stay, not merely nearby scenery. Ski lifts are not required.

## 5. Meal-plan filter and tariff semantics
Exact tariff classes:
- `Без харчування`
- `Сніданок`
- `Дворазове`
- `Триразове`

All available classes active by default. No `Неважливо`. Do not show All Inclusive until the dataset actually supports it sufficiently.

Exact semantics: `Сніданок` does NOT mean breakfast-or-better; `Дворазове` does NOT include full board. A hotel may have multiple real bookable tariffs and therefore belong to multiple meal-plan classes.

Filtering operates on tariffs; results are hotels. A hotel remains if at least one of its tariffs matches an active meal class.

### Main price rule
For each hotel, the main displayed price is the CHEAPEST tariff among currently active meal-plan classes for the active trip scenario. This same selected tariff drives:
- displayed 7-night price,
- `Вартість ↑`,
- max-price filter,
- value calculation input.

Do not secretly prefer breakfast. If all meal classes are active and RO is cheapest, RO is the main price. If breakfast is included in the cheapest tariff and cannot be removed, visibly mark this as value (`✓ Сніданок включено`).

If multiple tariffs exist, show alternatives compactly and directly, not as duplicate hotel cards and preferably not hidden in a dropdown. Example: `Сніданок — 31 500 грн · Дворазове — 38 000 грн · Триразове — 44 000 грн`.

When possible, normalize alternatives to the same 7-night dates and active guest scenario. If a full total cannot be reliably calculated, preserve the source condition exactly (e.g. `+650 грн/особу/добу`).

## 6. Wellness filters
No wellness requirement selected by default. Selected requirements combine with AND.
Core current controls:
- `Критий басейн`
- `Сауна`
- `Хамам`
- `Джакузі`
- `Тренажерна зала`

Strict filtering must use canonical structured evidence. UNKNOWN must not silently become NO.

Dynamic rule: a characteristic becomes a global filter only when enough current hotels support it for the filter to produce a useful selection. Rare features stay on cards; zero-support features are omitted. Current examples: salt room = card detail; aquapark/slides = card detail; chan = omit until enough evidenced hotels appear. Re-evaluate as the dataset grows.

Presence and price/access are separate facts. A hotel with a pool or SPA for an extra fee still matches the presence filter; the fee/access condition is shown on the card.

## 7. Seven-night price filter
- One maximum slider only: `Вартість 7 ночей`.
- Right endpoint: `Без ліміту`.
- NO fixed 20,000 UAH minimum. Scale must be able to extend down to zero / below the current cheapest property so future cheaper discoveries are not excluded by UI design.
- Uses the active scenario and the main matching tariff defined above.
- Do not automatically add SPA usage fees to 7-night accommodation cost when the number of SPA visits is unknown.

## 8. Hotel card — upper section
### Hero
- Large meaningful exact-property photo: property/resort/territory or defining SPA; weak generic landscape/bed/decor is not an acceptable hero when a better exact-property image exists.
- Overlay: `Наша оцінка 8,8` (example). This is our integral score.
- Keep badges restrained; no visual garland.

### Identity and map
- Hotel name.
- Oblast + settlement.
- Exact address when verified.
- Direct Google Maps point/link so one click shows where the property is.

### Independent reputation
Show multiple current independent sources when available, compactly, each with BOTH rating and review count, e.g.:
- `Booking 9,2 · 487 відгуків`
- `Google 4,6 · 1 240 відгуків`
- `Tripadvisor 4,5 · 190 відгуків`
- Hotels24 / Agoda etc. when reliable data exists.
Do not mix these visually with `Наша оцінка`.

## 9. Hotel card — price/value
Price belongs high on the card, before detailed SPA/description.
Example:
`28 000 грн · 7 ночей`
`4 000 грн/ніч · Без харчування`

Or:
`31 500 грн · 7 ночей`
`4 500 грн/ніч · ✓ Сніданок включено`

Show price/night as a secondary convenience figure.

`Ціна / якість` is a separate internal numeric score used for sorting. Do NOT show the numeric value score. Hotels that are genuinely high on value may receive a restrained `Ціна / якість` badge. The badge may change with scenario/tariff/current price and must remain selective enough to mean something.

Included benefits should be visually legible when they materially explain value: e.g. `✓ Сніданок включено`, `✓ SPA включено`. Do not change pure `Вартість ↑` sorting to compensate for those benefits; value sorting handles the richer comparison.

## 10. Hotel card — SPA and useful features
Prefer concise structured text over many badges.
Example:
`SPA: критий басейн · фінська сауна · хамам · джакузі`
Then a small number of decision-relevant accents such as `✓ SPA включено` or `Аквапарк`.

Do not force useful evidence into a poorer template. Show the most specific verified fact:
- source says only extra fee -> `SPA за доплату`;
- source says 500 UAH/day -> `SPA · додаткова оплата 500 грн/день`;
- 500 UAH/visit -> say per visit, not per day;
- child SPA until 19:00 -> state exactly that;
- included only for Deluxe -> state exactly that.

Rare useful features (salt room, snow room, aquapark, child pool, etc.) may be compact text or at most a few accents. Avoid 5–10 colorful chips/garland.

General content rule: structure provides order, but presentation is driven by usefulness and specificity of verified information, not by filling every template field.

## 11. Child scenario inside card
Render ONLY in `З дитиною · 10 років`.
The main card price must already be the complete applicable 2+1 7-night price when it can be reliably calculated; do not show couple price and hide the child supplement below.

Then explain useful specifics, e.g.:
- placement / extra bed and exact supplement,
- child meal inclusion or exact supplement,
- child SPA access/hours,
- kids club, child pool, aquapark,
- `Дитина без доплати` when verified and genuinely relevant.

Use the most specific evidence available; UNKNOWN remains explicit/neutral rather than invented.

## 12. Room and booking conditions
Do not recreate a full OTA room catalogue. Show the room/tariff on which the main displayed price is based.
Useful examples:
- room name, size, bed type,
- balcony / mountain view if decision-relevant,
- free cancellation deadline,
- pay at property / prepayment,
- low inventory when current and verified.
Do not clutter with standard amenities (TV, hair dryer, slippers, etc.) unless unusually relevant.

## 13. Editorial analysis
Do NOT copy hotel marketing slogans. Official sites/OTAs are evidence sources, not prose sources.
Provide a calm original analysis based on verified facts:
- concrete strengths,
- meaningful compromises/limitations,
- how the property differs from current alternatives,
- why it may matter for this exact late-October trip.
No promotional superlatives without evidence.

## 14. Sources and freshness
Card footer stays compact:
`Перевірено: DD.MM.YYYY · HH:MM`
plus direct source links used for the property.

Whenever useful, attach the exact source to the fact it supports, especially price/promotion/availability conditions. Example: main price can link directly to the Booking/official tariff source.

Property verification time is separate from the page-level latest meaningful update time.

## 15. Cross-cutting product rules
1. Chat is NOT the durable source of project knowledge. Significant decisions, discoveries, architecture changes, accepted/rejected semantics and implementation checkpoints must be written to durable project state in GitHub (or canonical Drive docs when appropriate).
2. Prefer a small useful UI over a feature catalogue: frequent + decision-relevant -> filter; rare -> card detail; zero -> omit; re-evaluate dynamically as the dataset grows.
3. Do not reduce specific source evidence to generic wording.
4. Do not fabricate uniformity: cards may have different evidence depth.
5. Scenario relevance controls visibility; irrelevant information should disappear rather than merely move lower.
6. Tariff price, filters and sorting must use consistent semantics.
7. Deduplicate physical properties before deriving counts/filter support.
8. Structured feature fields must preserve UNKNOWN separately from NO.

## 16. Next implementation interpretation
This spec is the agreed UX target. Implementation should proceed in coherent, testable slices while respecting the existing Phase A canonical-photo/data debt and without creating a second shadow data model. Material future UX decisions must update this durable spec before/with implementation.
